# Backend

This document explains how the FastAPI backend is built and why: the module layout and when to split it, the request guards and rate limiter, key handling and rotation, every validation rule and business constant, the logging and audit events, error handling, the test approach, the measured performance, and the tools that were deliberately not adopted. It is for developers changing [backend/main.py](../backend/main.py), [backend/ops.py](../backend/ops.py) or [backend/test_api.py](../backend/test_api.py). Endpoint contracts are in [API.md](API.md); the data model and transactions are in [ARCHITECTURE.md](ARCHITECTURE.md).

## Module layout

| File | Lines (about) | Contents |
|---|---|---|
| `backend/main.py` | 640 | The whole API, top to bottom: environment and constants; `fp()` and `audit()`; the catalogue data (`MATERIALS`, `SLOTS`, `TIERS`, `REWARDS`, `MISSIONS`, `DISTRICTS`); `db()`, the `MIGRATIONS` ladder, `init_db()`, `seed()`, `estimate()`, `expire_overdue()`; the request guards (`client_ip`, `bucket_key`, `throttle`, `charge`, `guard`, `require_key`, `BodyLimit`); the lifespan; the app and its exception handlers; `log_path()` and `Observe`; the routes |
| `backend/ops.py` | 90 | Operator commands, stdlib only: `backup DIR` and `check` |
| `backend/test_api.py` | 920 | The regression suite: 47 sections, no test framework |
| `backend/requirements.in`, `requirements-dev.in` | | Direct dependencies; the source of truth |
| `backend/requirements.txt`, `requirements-dev.txt` | | Hash-locked trees generated by `uv pip compile` |

Runtime dependencies: FastAPI 0.142.4, Starlette 1.7.0, Pydantic 2.13.5, uvicorn 0.53.0 with httptools 0.8.0 and uvloop 0.22.1. Test only: httpx 0.28.1; the suite prints Starlette's deprecation warning about using httpx with `TestClient` (it suggests `httpx2`), which does not fail the run; take the swap when Dependabot proposes it. Python 3.12 is required (`sqlite3.connect(..., autocommit=True)` in `init_db()`).

### When to split `main.py`

Not yet. One readable file is cheaper than a package while there is one user, one worker and one contributor. The tech-lead review set the triggers and the order:

| Trigger | Split |
|---|---|
| Real accounts land (phase B), a second contributor joins, or a second worker process starts | 1. `security.py`: `guard`, `throttle`, `bucket_key`, `charge`, `require_key`, `BodyLimit`, `Observe`, `log_path` (no business logic; their tests are already separate sections) |
| | 2. `db.py`: `db()`, `MIGRATIONS`, `init_db()`, `seed()` |
| | 3. Routers by actor: citizen, collector, partner (`APIRouter`, a `/api/v1` prefix for external clients) |

`init_db()` runs at import on purpose: the suite and the CPU benchmark write rows right after import through a `TestClient` that never enters the lifespan. The ladder and the seed take the write lock first, so several workers can run it at once.

## Request guards

`guard()` is an app-wide dependency (`FastAPI(dependencies=[Depends(guard)])`), so no route can forget it.

1. **CSRF, POST only.** 415 unless `Content-Type` starts with `application/json`; 403 for `Sec-Fetch-Site: cross-site`. A cross-site `<form>` can send neither, so these already hold for the cookie sessions of phase B; `SameSite=Strict` on that cookie completes the set. They run before the charge, so a cross-site page cannot drain a visitor's bucket.
2. **Rate limit.** `charge()` takes one token. POSTs and `GET /api/codes/{code}` use the write bucket (`BURST` 10, `REFILL` 0.5/s, `Retry-After: 2`); other GETs the read bucket (`READ_BURST` 60, `READ_REFILL` 2/s, `Retry-After: 1`, key suffix `|r`).
3. **Malformed bodies.** FastAPI parses a JSON body before it runs dependencies, so a body that is not JSON never reached `guard()`. The 422 handler runs `guard()` when `scope["throttled"]` is not set, so such a request is CSRF-checked and charged too.

The limiter (`throttle()`) is a token bucket in a module dict under a `threading.Lock`:

- Key: `bucket_key(client_ip(request))`. IPv4 and IPv4-mapped addresses are their own key; IPv6 is keyed per /64, because one client usually holds a whole /64; anything else is `h:` plus a 16-hex sha256 prefix, so a forged header cannot make keys of arbitrary size.
- Client: with `TRUST_PROXY=1` the rightmost `X-Forwarded-For` entry (the one the edge wrote); else the TCP peer. Uvicorn runs with `--no-proxy-headers`, because by default it would trust `X-Forwarded-For` from 127.0.0.1.
- Idle sweep: when the dict holds more than 10,000 keys, buckets idle for more than 120 s are dropped, at most once every 10 s, so a call stays O(1) amortized.
- Time source: the module attribute `clock` (`time.monotonic`), which the tests replace.
- Edge bypass: with `TRUST_PROXY=1`, a request (other than `/api/health`) whose `X-Forwarded-For` is missing or has more than one entry logs `event=edge_bypass xff_entries=N` at WARNING. The edge always sends exactly one.
- Ceiling: the dict is per process. A second API instance needs a shared store (the `ponytail:` comment in `throttle()` names Redis).

`BodyLimit` (pure ASGI) answers 413 for a `Content-Length` over `MAX_BODY` and stops a streamed body as soon as the count passes it. Next.js additionally caps the copy it buffers at 16 KB (`proxyClientMaxBodySize`), but it does not reject a larger body itself; the 413 comes from FastAPI.

## Keys

`COLLECTOR_KEY` and `PARTNER_KEY` are shared secrets read once at import by `env_keys()`.

- **Format.** A comma list; whitespace around entries is stripped. Each key needs 32+ characters and 10+ distinct characters, or the process exits with a message naming the variable and how to make a key (`python -c 'import secrets; print(secrets.token_urlsafe(32))'`).
- **Check.** `require_key()` compares the presented header, as bytes, with every configured key using `secrets.compare_digest`, OR-ing the results without short-circuiting, so the timing does not tell which key matched. Bytes, because `compare_digest` raises on non-ASCII strings (that was a 500).
- **Failure.** Unset, missing and wrong keys all get the same 403 `{"detail": "forbidden"}`, so a scanner cannot tell a half-configured deploy. The log line `event=auth_fail header=<name> reason=unconfigured|missing|mismatch fp=<sha256[:6] or ->` tells the operator which.
- **Attribution.** On success the handler logs the presented key's fingerprint (`key=<sha256[:6]>` on `complete` and `code_use`), so operators can see when an old key stops being used.
- **Rotation.** Set `new,old`, restart, move clients to the new key, watch the old fingerprint disappear from the logs, set `new`, restart. Steps in [OPERATIONS.md](OPERATIONS.md).

| Constant or rule | Value | Where | Reason | Status |
|---|---|---|---|---|
| `PICKUPS_PER_DAY` | 5 pickups created per Tehran day, canceled ones included | `create_pickup` | Farming cap for the single demo user; counted under the write lock | product rule, confirm |
| `MAX_PICKUP_KG` | 50 kg per material and 50 kg total per pickup | `PickupIn` | Complete pays for the declared items within ±10%, so this caps one mint at 15,000 points (16,500 with the jitter) | product rule, confirm |
| Minimum per material | 0.5 kg | `PickupIn` | Smallest meaningful bag | product rule, confirm |
| Day window | today to today + 14 days | `create_pickup` | Bookable horizon; the UI offers fewer days | product rule, confirm |

## Logging and audit events

`audit(event, request, level, **fields)` writes one `event=<name> rid=<rid> k=v …` line; `rid` is `-` outside a request. Values are URL-quoted. `fp()` makes the sha256 prefixes.

| Event | Level | Fields | When |
|---|---|---|---|
| `startup` | WARNING in demo mode or when a key is unset, else INFO | `demo`, `trust_proxy`, `collector_key_set`, `partner_key_set` | Lifespan start |
| `expire_overdue` | INFO | `count` | Each sweep |
| `expire_overdue_failed` | ERROR, with traceback | | A sweep raised; the loop continues |
| `create_pickup` | INFO | `pid`, `kg`, `est` | A pickup was booked |
| `complete` | INFO | `pid`, `points`, `kg`, `key` (sha256[:6], or `-` in demo) | A pickup was credited |
| `cancel` | INFO | `pid` | A pickup was canceled |
| `redeem` | INFO | `reward`, `code` (sha256[:8]), `balance` (after) | A reward was redeemed |
| `code_use` | INFO | `code` (sha256[:8]), `key` (sha256[:6]) | A partner spent a code |
| `mission_correct` | INFO | `mission`, `points` | A mission paid out |
| `auth_fail` | WARNING | `header`, `reason` (`unconfigured`, `missing`, `mismatch`), `fp` | A key check failed |
| `edge_bypass` | WARNING | `xff_entries` | `TRUST_PROXY=1` and `X-Forwarded-For` missing or multi-entry |
| `db_busy`, `db_error` | ERROR | `error` (first 80 characters) | `sqlite3.OperationalError` became a 503 |
| `backup` (ops.py) | INFO / ERROR | `ok`, `bytes`, `file` / `ok=0`, `reason` | `python ops.py backup DIR` |
| `ledger_check` (ops.py) | INFO / ERROR | `ok`, `reason` (`-` or the broken invariant names) | `python ops.py check` |

The access line (`Observe`) is described in [ARCHITECTURE.md](ARCHITECTURE.md). The suite checks that no full key, address, full code or newline reaches any line (`log_hygiene`, `business_events`).

Not logged on purpose: 404s under `/api/codes/` and bursts of 422 stay at INFO, and there is no points-awarded alarm threshold. Both wait for an alerting pipeline.

## Error handling

| Failure | Response | Where |
|---|---|---|
| Business rule (`HTTPException`) | Its status and a static `detail` string | Handlers |
| Request model validation | 422 with `loc`, `msg`, `type` per error, never the input | `invalid()` |
| `sqlite3.OperationalError` (lock past 5 s, read-only or full volume) | 503 `database unavailable, retry shortly`, `Retry-After: 1`; logged `db_busy` or `db_error` | `db_unavailable()` |
| Body over 16 KiB | 413 | `BodyLimit` |
| Anything else | Starlette's 500; the access line logs it at ERROR | |

Error bodies are static strings. The OperationalError text goes only to the log, cut to 80 characters. Path parameters are bounded (`Pid` is 1 to 2^63-1, codes at most 40 characters) so an out-of-range value is a 422, not an SQLite `OverflowError`.

## Testing

`backend/test_api.py` is a dependency-free assert runner (FastAPI's `TestClient`, which needs httpx).

- **Sections.** Each test is a function under `@section`. 47 sections, grouped as pickups; points, rewards, codes and missions; keys; storage; `ops.py`; request pipeline.
- **Isolation.** Before each section, `fresh()` restores every patched module setting, lifts the daily cap and the bursts, clears the buckets, points `main.DB_PATH` and `ops.DB_PATH` at a new temporary database, seeds the weighing jitter (`random.seed(7)`) and runs `init_db()`. Sections pass in any order.
- **Time.** Burst tests set `REFILL` to 0, so a slow host cannot refill a token mid-test. Refill tests replace `main.clock` with a fake clock at exactly representable times. "Today" is read when used, never at import; `main.today` and `main.ts` are patched for the Tehran-midnight test.
- **Concurrency.** `fanout()` fires 8 requests from a thread pool: redeem races at one and two tickets' balance, complete races, parallel creates at the daily cap.
- **Processes.** `production_mode` starts a fresh interpreter with a clean environment; `weak_keys_stop_startup` calls `env_keys()` in-process and expects `SystemExit`; `ops_cli` runs `ops.py` the way compose does.
- **Output.** Every failing section prints its traceback and the run continues; the exit code is 1 if any failed, and `ok` prints only when all pass.

```bash
cd backend
python3 -m venv .venv && .venv/bin/pip install --require-hashes -r requirements-dev.txt
.venv/bin/python test_api.py                                   # all 47 sections; prints ok
TEST_ONLY=redeem_races,daily_cap .venv/bin/python test_api.py  # only these sections
TEST_SHUFFLE=31337 .venv/bin/python test_api.py                # shuffled order, reproducible by seed
```

**Mutation check.** The builder planted 8 deliberate bugs in `main.py`, one at a time, and each was caught by its section: redeem `>=` changed to `>`; the slot tie-break removed; the day bound removed; the 422 handler not charging; codes logged in clear; health skipping the write; the total weight cap removed; reads unthrottled. The mutation script is not in the repository; to repeat the check, make each change by hand and run the suite.

## Performance

CPU time per request (process CPU, best of 7, in milliseconds) on a database with 10,000 pickups and 10,000 transactions, through `TestClient`. CPU time is used instead of wall clock because it stays stable under background load. "Before" is the code before the follow-up pass, "after" is the current code, both with the same benchmark (it writes synthetic credits with refs `b0`..`b9999`, because the unique index refuses refs that duplicate the demo seed's).

| Endpoint | Before | After |
|---|---|---|
| `GET /api/state` | 47.42 | 45.46 |
| `GET /api/city` | 48.40 | 49.03 |
| `GET /api/pickups` | 11.63 | 12.58 |
| `GET /api/catalog` | 7.07 | 8.00 |
| `POST /api/rewards/bike/redeem` | 9.56 | 11.68 |

- The GET differences of about 1 ms are noise: the new per-request work measures 19 to 30 µs for `charge()` and 4 to 10 µs for `log_path()`.
- Redeem's +2.1 ms is mostly the second `SUM` for the audit line's balance (about 1.57 ms at 10,000 rows), marked with a `ponytail:` comment.
- `synchronous=FULL` costs about 2.1 to 2.5 ms of wall clock per commit over `NORMAL` (median of 40 interleaved rounds, measured twice).
- The benchmark script is not in the repository. The earlier, larger gains (for example `GET /api/pickups` from 931 ms to 11 ms) are in [../SECURITY_AUDIT.md](../SECURITY_AUDIT.md), "Backend performance".

## Not adopted, and when to adopt

| Tool | Why not now | Trigger to adopt |
|---|---|---|
| Alembic | There is no ORM; the `user_version` ladder is a dozen lines and runs atomically under the write lock | An ORM is adopted, or migrations need downgrade scripts or branch merges |
| SQLAlchemy | Every query is short, parameterized SQL next to its handler | A second database engine (for example PostgreSQL), or query composition the handlers can no longer read |
| Celery | The only background job is one idempotent hourly `UPDATE`, run by a lifespan task | Work that must survive restarts with retries beyond one in-process loop, for example the SMS sending of phase D at volume |
| Redis | The token buckets are correct for one process | A second API process or instance |
| Prometheus or OpenTelemetry | One access line per request with id, status and latency, plus audit lines, covers one instance | A metrics scraper or alerting pipeline exists, or the system becomes more than one service |
| pytest rewrite | The assert runner is isolated, shuffleable and has no dependency | Shared fixtures across files, or the suite outgrows one file |
